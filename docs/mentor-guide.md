# Методическое руководство

Проводите кейсы в порядке Linux → Docker → CI → Monitoring. До команды студента спрашивайте: какое состояние он ожидает увидеть, чем команда подтвердит или опровергнет гипотезу и как будет доказано исправление. Не раскрывайте закрытые материалы на общем экране.

## Case 1

Оценивайте переход от симптома к журналу и конкретной проверке, а не скорость. После занятия используйте reset или cleanup.

## Case 2

Попросите объяснить image и container, `COPY`, `WORKDIR`, разницу `RUN`/`CMD`, port mapping, environment и healthcheck.

## Case 3

Вопросы для защиты:

- Как GitHub понимает, когда запускать workflow?
- Что такое job?
- Что такое step?
- Почему workflow стал красным?
- Где именно ты увидел причину?

Вносите дефект только после первого зеленого run и коммитьте его в student-репозитории как отдельное изменение.

## Case 4

Попросите показать target status, два осмысленных запроса PromQL, изменение графиков при нагрузке, переход `up` в 0 и обратно, затем runbook. Внешний вид dashboard оценивается вручную.
